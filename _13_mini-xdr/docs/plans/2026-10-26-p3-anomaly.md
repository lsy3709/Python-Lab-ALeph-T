# 미니 XDR P3 — 행위 이상탐지(기준선·z-score) 구현 계획

> **에이전트 작업자용:** 필수 하위 스킬 — `superpowers:subagent-driven-development`(권장) 또는 `superpowers:executing-plans` 로 작업 단위 실행. 단계는 체크박스(`- [ ]`)로 추적.

**목표:** 출발지 IP·계정의 1시간 버킷 특징을 기준선과 비교해 robust z-score 를 내고, 임계(기본 3.0)를 넘으면 `behavior` 계층 이벤트를 `events_norm` 에 넣어 상관기가 인시던트에 붙이게 한다. LLM 은 쓰지 않는다.

**설계:** [186] 4-2. 순수 함수(`app/anomaly.py`: 버킷·특징·기준선·점수·이벤트) + 실행기(`app/detector.py`: 기준선은 시간이 바뀔 때만 다시 계산, 매 주기 최근 2개 버킷만 채점). 워커 주기는 재연결 → 수집 → **이상탐지** → 상관.

**기술:** 표준 라이브러리 `statistics`·`math`(새 의존성 없음) · 기존 PyMySQL · Flask 콘솔

## 라이브 랩에서 확인한 사실 (2026-10-26)

| 항목 | 값 |
|---|---|
| IP × 1시간 버킷 | 383개 — 시간당 이벤트 중앙값 18 · MAD 척도 16.3 · p90 39 · 최대 36,425(폭주) |
| 개인 기준선 가능(활동 30시간↑) | IP 2개(192.168.120.1 179시간 · 127.0.0.1 36시간), 최근 14일은 1개 / 계정은 lsy 29시간(로그인 성공 28회) |
| 로그인 실패율(로그인 있는 IP 버킷 81개) | 중앙값 0.857 · 척도 0.212 — 0 이 30개, 1 이 35개 → 위로 벗어날 여지가 없어 이상 판정에 쓸 수 없음 |
| 404 비율(앱 이벤트 있는 IP 버킷 154개) | 중앙값 0 · 척도 0 → 척도 하한 필요 |
| 신호 종류 수 | 중앙값 1 · 척도 0 · 최대 6 |
| 로그인 성공 시각(KST) | 05~20시에 퍼져 있음(68건) |
| 요청 경로(URL) | 저장하지 않음 → "접근 경로 다양성" 계산 불가 |

## 설계 결정

1. **특징 5개(설계 → 실데이터 맞춤)**

| [186] 설계 | P3 특징 | 이유 |
|---|---|---|
| 분당 요청률 | `events` 시간당 이벤트 수 | 모든 요청이 아니라 보안 신호만 저장되므로 "신호 발생량" |
| 404 비율 | `ratio_404` (web-scan·100230 / 앱 계층 이벤트) | 그대로. 척도 하한 0.2 |
| 로그인 실패율 | `login_fail` 시간당 로그인 실패 수 | 실패율은 집단 중앙값 0.857 이라 무의미 → 양으로 |
| 접근 경로 다양성 | `signals` 신호 종류 수 | 경로 미저장 → "한 시간에 몇 종류의 공격 단계를 시도했나" |
| 로그인 시간대 | `login_hour` (계정, KST, 원형 통계) | 23시와 1시는 2시간 차이 — 원형 평균·원형 표준편차 |

2. **robust z** = (값 − 중앙값) / max(1.4826 × MAD, 하한). 폭주·공격이 섞인 기준선에서도 중심이 끌려가지 않는다. 하한: events 1 · signals 1 · login_fail 1 · ratio_404 0.2 · login_hour 1시간.
3. **한쪽 판정**: 4개 버킷 특징은 큰 값만 이상(조용해진 것은 위협 신호가 아님). `login_hour` 는 평소 시각과의 원형 거리.
4. **2단 기준선**: 개인(그 엔티티 표본 ≥ 30) → 없으면 **집단**(같은 유형 전체, `entity='*'`) → 그것도 30 미만이면 "기준선 부족"(채점 안 함 — [186] 콜드스타트 원칙). 표본 = 활동이 있었던 1시간 버킷(조용한 시간은 표본이 아님), login_hour 는 로그인 1건이 표본 1개.
5. **학습·채점 분리**: 기준선 = `[현재 시각 − BASELINE_DAYS, 직전 버킷 시작)`, 채점 = 직전 버킷 + 현재 버킷(채점 대상이 자기 기준선에 섞이지 않음). 기준선은 시(hour)가 바뀔 때만 다시 계산하고 `baselines` 테이블을 통째로 교체(트랜잭션).
6. **behavior 이벤트**: `layer=behavior, source=anomaly, event_type=anomaly-<특징>-<구간>`(구간 z3·z5·z8 → 지문의 "이상점수 구간"), `src_ip`= IP 엔티티면 그 IP, 계정이면 그 버킷에서 가장 많이 쓴 IP(→ IP 인시던트에 붙음), `ts`= 버킷의 마지막 이벤트 시각, `raw_ref`= `anom:` + SHA-1(유형·엔티티·특징·버킷) — 같은 버킷을 매 주기 다시 채점해도 **INSERT IGNORE 로 한 번만** 들어간다. level 은 비움(규칙 하한을 올리지 않음).
7. **이상 점수 이력**: 새 behavior 이벤트가 들어간 때만 `anomaly_scores` 에 특징별 값·z·기준선 종류(JSON) 1행.
8. **사후 분석 CLI** `python -m app.detector --report`: 전체 기간 기준선으로 과거 버킷을 훑어 특징별 이상 버킷 수·상위 목록을 출력(쓰기 없음, 미래 데이터가 기준선에 섞이는 사후 분석임을 표시).
9. 콘솔 `/anomalies`: 최근 이상 점수·기준선 요약(읽기 전용 연결).
10. 설정: `BASELINE_DAYS`(30) · `BASELINE_MIN_SAMPLES`(30) · `ANOMALY_Z`(3.0).
